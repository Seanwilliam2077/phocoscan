# 原生 iPhone 扫描引导与数据价值验证计划

> 2026-11-03 产品顺序更新：首版开发 **原生 iPhone 扫描 App + FF／WorldMirror2 预览**，传统 COLMAP／SfM 属于另一条仍在开发的算法路线，不作为首版依赖。游戏只做成长记录。产品纵切及验收见 [首版交付范围](NATIVE-FF-APP-MVP.md)；本文保留研究验证路线，未完成事项不能写成已验证。

## 要回答的三个问题

1. 一部普通 iPhone 能否在不牺牲干净 RGB 原片的前提下，稳定记录逐帧时间、相机参数与跟踪；LiDAR iPhone 能否额外记录对齐的深度与置信度？
2. 同一份真实采集能否支持快速 3DGS 预览、独立的 SfM／精建，以及可审计的视频数据和机器人场景派生数据？“可生成资产”“可用于训练”和“能提升模型”是不同结论。
3. 端上提示能否让非专业用户采到更好的多视角数据，同时保持操作简单？成长记录是否让他们愿意完成第二、第三次扫描，单独作为小规模产品观察。

当前 T0 的最短闭环为：**iPhone 系统相机原片 → 本地哈希与多视角选帧 → WorldMirror 提交与真实终态 → PLY／SOG 结构核对 → 查看资源与原视频对照**。后续原生 App 演示路线再扩展为本地可恢复采集包、稳定 HTTPS 上传、异步预览和成长记录。快速重建失败不删除原片；成长奖励只代表服务器确认了新采集，不代表质量通过。传统慢环和正式机器人／视频模型训练不属于本轮 FF 验收。

## 平台与实施边界

- 客户端采用 Swift／SwiftUI + ARKit，复用 `ios/PocketWorld.xcodeproj` 作为起点，先核实其编译、签名与真机安装状态；旧小程序仅作 API、草稿恢复和养成规则的参考，不继续作为玩家端。
- 需要可运行 Xcode 的 Mac 构建环境、有效的 iPhone 开发签名与真实设备。Windows 可以编辑源代码、运行 Node 后端和离线分析，但不能把 Windows 上的源码检查称为 iPhone App 验收。先记录设备型号、iOS 版本、是否有 LiDAR；至少一部普通 iPhone 参加采集测试，LiDAR Pro 机型用于深度增强和几何基准。若首轮只有一部普通 iPhone，先做 RGB＋ARKit 位姿支线，LiDAR 测试标记为待设备。
- 本轮已确认一部 **iPhone 17 Pro Max（带 LiDAR）** 和一台 Mac，暂未有付费 Apple Developer 会员。先用 Xcode 的 Personal Team 为本人设备做开发签名与安装；Xcode 是否已安装、手机 iOS 版本及 Mac 到工程的同步方式仍需在执行时记录。普通 iPhone 的无 LiDAR 对照组仍是判断大众 C 端可扩展性的后续必测项。[Apple 设备规格](https://support.apple.com/en-la/125091)
- 以 `ARSession` 的同一条帧流作为首轮 RGB、时间、位姿和内参来源；`ARFrame.capturedImage` 是无游戏叠层的相机像素缓冲，`ARFrame.timestamp` 和 `ARCamera` 提供对应元数据。对视频编码前后逐帧核对时间、方向、裁剪与分辨率。不要假设另开 `AVCaptureSession` 能与 ARKit 同时稳定占用后置相机。LiDAR 深度仅在 `supportsFrameSemantics(.sceneDepth)` 为真时启用，缺失时写 `null` 而不是估算值。参考 [Apple ARFrame](https://developer.apple.com/documentation/arkit/arframe) 和 [sceneDepth](https://developer.apple.com/documentation/arkit/arconfiguration/framesemantics-swift.struct/scenedepth)。
- 在拍摄中保留低成本的运动、重叠、跟踪状态提示；服务端只接收异步重建任务。首轮只在拍摄结束或达到足够覆盖后提交一次 8–16 帧的 FF 任务。官方 WorldMirror 接口是对一组图像／视频运行的推理管线，不能把多次从头重建称为增量推理。
- 后端至少分离 API／数据库／私有原片存储、持久任务队列、GPU worker。手机只连稳定 HTTPS 业务入口，不直连内网 Hub。Codespaces 和 Cloudflare Quick Tunnel 只适合短时联调，不作为测试计划的稳定服务。上传协议要固定 `captureId`、文件哈希和幂等提交，断网、杀进程、重启后能从本地草稿恢复。

### 无 LiDAR 机型也是主采集路径

Apple 的 [iPhone LiDAR 机型清单](https://support.apple.com/en-by/121825)列出 iPhone 12 Pro／Pro Max 至 18 Pro／Pro Max；普通数字款、mini／Plus、Air、e、SE，以及 11 Pro 和更早机型没有后置 LiDAR。设备能力应在运行时检测，不能只按机型字符串决定。Apple 明确说明 `sceneDepth` 只在 LiDAR 设备支持；[ARKit 世界跟踪](https://developer.apple.com/documentation/ARKit/managing-session-life-cycle-and-tracking-quality)仍可由图像和惯性传感器提供相机位姿。

首轮客户端把无 LiDAR 作为正常模式：从同一 `ARFrame` 保存 RGB、时间戳、相机内参和位姿，`depthSupported=false`、逐帧深度为 `null`、服务端回执为 `depthStatus:not_captured`。快环以多视角 RGB 跑 FF 预览；慢环用独立 SfM／多视角几何估计深度并记录算法来源，不能将估计值标为 LiDAR 测量。引导重点是保持静态参照、连续画面重叠、侧向位移和少量斜角，提示跟踪差、运动过快、低纹理和动态物体。机器人分支必须另用已知尺寸标记／实测距离校准尺度，并单独检验碰撞网格。普通机型与 Pro 机型分别统计完成率、跟踪、重建与尺度误差；当前无 LiDAR 代码路径尚未真机验证。若设备不支持 `ARWorldTrackingConfiguration`，当前 App 会报不支持，纯视频＋服务端 SfM 回退须单独实现和验收。

### T0：普通 iPhone 视频＋虚拟机预试验

在 Xcode 和原生 App 真机就绪前，可用 iPhone 系统相机拍摄 3 个静态、有纹理的物体、室内与室外样本，每段约 15–30 秒。保留原始 MOV，通过数据线、AirDrop 或文件共享送到 Windows/Linux 主机或虚拟机；两端记录文件 SHA-256。用 [T0 视频工具](T0-VIDEO-PILOT.md)从实际帧时间选出 8／16 张画面，人工核对侧向视差和重叠，再用现有 [WorldMirror operator CLI](WORLDMIRROR-INTEGRATION.md) 的 `upload → quick → resume → inspect` 跑 FF 重建。核对固定输入资产、帧数和 revision、真实成功终态、PLY 哈希与结构、查看效果和分项耗时。若虚拟机无 GPU，继续调用既有远程 Hub。2026-11-02 的独立合成 GPU 健康任务已成功，真实 iPhone 场景仍待原片；见 [T0 实测记录](T0-VALIDATION-2026-11-02.md)。传统 [COLMAP CPU](T0-COLMAP.md) 工具保留为后续独立算法研究，本轮不用。

这项试验可回答 RGB 多视角能否产生有用的预览、上传／推理链路耗时和哪些场景失败。iPhone 系统相机视频不包含与每帧同步的 ARKit c2w、内参、`sceneDepth`；即使使用 Pro 机型，也不能把视频标为 RGB-D 或真实 ARKit 轨迹。当前 v2 接口要求同源逐帧元数据，v1 的 `in_app_rgb` 又会把系统相机视频误记为 App 内采集。因此 T0 优先用直接 operator CLI；若要由 iPhone 真正向业务服务器上传，需另建明确标为 `external_rgb_video` 的导入路径和 HTTPS 入口。虚拟机／iOS Simulator 不能验证 ARKit 相机、LiDAR、实时引导或原生上传体验；[Apple 明确说明 ARKit 不支持 iOS Simulator](https://developer.apple.com/documentation/arkit/tracking-and-visualizing-planes)。

## 同源采集包与派生边界

采集包在手机上先落盘，再提交。目录示例；文件名和 JSON 版本固定在实现时由测试校验。所有原件使用 SHA-256，服务端按 `captureId` 拒绝不同内容覆盖。

```text
capture/<captureId>/
  manifest.json              # schemaVersion、sceneId、设备／镜头、同意版本、采集模式、UTC 开始时间、时钟来源
  rgb.mp4                    # ARFrame 相机像素编码的连续原片，不含游戏 UI；明确音频策略
  frames.csv                 # frameId、ARFrame 单调时间、视频 PTS、原图尺寸、方向、跟踪状态、丢帧标记
  cameras.jsonl              # frameId、K、ARKit c2w、坐标定义、跟踪重置事件；缺失字段为 null
  depth/                     # 有 LiDAR 时保存深度和置信度、尺寸、与 RGB 的对齐元数据
  checksums.sha256
```

不得用编码视频的固定帧率反推真实拍摄时间。每一帧的内参与像素分辨率要对应；ARKit、OpenCV、COLMAP 和 WorldMirror 坐标变换需在 `transform_chain.json` 里写出可逆矩阵与单位，记录 ARKit 跟踪重置。WorldMirror 即使使用相机先验也会相对首帧归一化，返回原 ARKit 坐标及尺度必须显式转换和实测，不能靠文件名宣称对齐。见[官方先验格式](https://github.com/Tencent-Hunyuan/HY-World-2.0/blob/main/DOCUMENTATION.md)。

从**同一个不可变的原始采集包**派生三条分支，每条有父 `captureId`、输入帧 ID、算法版本和哈希：

| 分支 | 可交付材料 | 首轮能得出的结论 |
|---|---|---|
| 玩家预览 | 8–16 个精选帧 → WorldMirror 轻量 3DGS／手机查看资源 | 是否能看、耗时与主观质量；不作为其他 AI 训练标签 |
| 视频数据 | 连续原片、逐帧时间、镜头运动、场景／隐私审核与使用授权 | 是否可入指定视频数据管线；不能只给离散关键帧，也不能凭可导出就声称提升视频模型 |
| 机器人数据 | 经独立许可链路得到的相机轨迹、尺度、深度／网格、语义与碰撞代理 | 能否装入一个明确的仿真任务；3DGS 外观本身不证明碰撞、摩擦或策略迁移可用 |

真实用户采集前明确告知用途、留存与删除机制，特别处理室内私人信息、室外路人和车牌。训练使用权与允许上传供预览是不同授权；未获训练许可的包仍可单独测试产品流程，但不得进入训练候选集。

## 现有 v1 API 与原生采集包的差额

当前 `server/` 的 `/v1/sessions` 契约只接收一个视频文件、可选封面以及提交元数据，且会话字段固定 `poseSource:"none"`、`calibrationAvailable:false`；它**不能**接收、核对或查询逐帧时间、相机矩阵、LiDAR 深度与坐标变换。先前的 `POST /v1/sessions` → `PUT /video` → `POST /submit` 仍可服务旧客户端或纯 RGB 兼容测试，不能把它的成功回执称为本计划的完整采集包通过。见 [现有合同](CONTRACT.md)。

原生纵切新增兼容的 v2 资源，而不静默改变 v1 语义：

1. `POST /v2/captures` 使用手机预生成的固定 `captureId`、场景和同意版本创建草稿；同一请求幂等，冲突内容拒绝。
2. `PUT /v2/captures/:id/rgb` 发送原片；`PUT /v2/captures/:id/metadata` 发送版本化清单、逐帧表、相机和可选深度压缩包。每个部件上传使用内容哈希与大小核对；大文件须支持分段续传或私有对象存储分片，重新授权不能改变 `captureId` 和对象键。开发实现可选择签名直传，但永久密钥只在服务端。
3. `POST /v2/captures/:id/complete` 在服务端核对原片／元数据哈希、帧数、时间单调性、必填字段及文件可解码性后，原子地标记 `verified`，返回唯一 `captureReceiptId`。缺深度的普通 iPhone 是合法输入，但在回执中如实标明 `depthAvailable:false`。失败保持可重试草稿，不能发成长回执或重建任务。
4. `GET /v2/captures/:id` 返回已接收部件、验证状态、同一个回执和各条处理任务状态，用于 App 杀进程／断网后恢复；快速与慢速任务分别按 `(captureId, pipelineVersion, taskKind)` 去重。

**2026-11-02 实现边界：**当前服务端 v2 纵切已实现原片与逐帧元数据的哈希核对、格式/时间检查和 `rgb_metadata_verified` 回执，尚未验证视频可解码，也未接收深度文件、启动重建任务或提供处理任务状态。因此上面的第 2–4 项是完整目标契约，不能把现有回执称为完整多模态采集或 FF/SfM 成功。现阶段 `decodeVerified:false`；LiDAR 文件仅有本机引用时为 `depthStatus:pending_upload`。

服务器现有的匿名令牌、私有文件存储和资产导回逻辑可以复用，但 v2 的认证、所有权、删除、留存与管理员导出都需明确新增测试。成长记录只是 `verified` 回执的一个可选呈现视图；关闭游戏也必须能完成 T1–T11 和数据导出。

## 场景与评测数据

保留原计划的桌面、房间、物体样本，并增加必需的室外局部场景。每类先由研究人员做 2 条完整参考轨迹，再采集漏侧面、移动过快、原地转圈、缺低／高视角等人为缺陷；最后让至少 10 名非项目成员按 App 提示自行拍摄 1–3 次。普通 iPhone 样本与 LiDAR Pro 样本分开统计；不能仅用 Pro 机型外推大众 C 端采集质量。

| ID | 场景 | 关键真值／风险 |
|---|---|---|
| S1 | 桌面和 3–5 个静止可操作物体 | 标记板、卷尺尺寸、物体边界与接触面；用于尺度、碰撞和简单操作 |
| S2 | 普通室内一角／房间 | 近中远层次、地面墙面和遮挡；注意光照与隐私 |
| S3 | 单物体及一件反光或透明难例 | 缺顶部／低圈、材质失败模式；难例单独报告，不并入普通样本平均值 |
| S4 | 室外街角／店面外立面或步道固定物 | 光照、移动行人／车辆、天空和大尺度；仅在安全、可拍摄的位置采集 |

缺陷 `labels.json` 要标注帧区间和空间区域，不能只写一句“漏了一侧”。每段测量真值写入 `ground_truth.json`，包括测量工具、时间与误差。评测视角使用**独立的拍摄路径或空间扇区**，不能每 8 帧抽一帧：相邻帧几乎相同会高估新视角质量。训练／验证划分按场景和采集人隔离，保留未见过的室内和室外位置。

## T1–T11：按依赖执行的测试矩阵

所有阈值都先当假设，固定设备、帧数、网络、场景和版本后再跑；不能为了“通过”而事后改条件。每项产出 `results/Txx/metrics.json` 和 `summary.md`，保留输入清单、原始日志、失败样本及偏离说明。

| 测试 | 先决条件与改法 | 核心记录／通过判据 |
|---|---|---|
| **T1 FF 时延／显存** | 先确认 GPU worker 可成功执行。现有 Hub 只接收 2–32 帧，先测 8／16／32；64／96 帧若用官方离线脚本，另列实验，不能混作 Hub 能力。L20 与 RTX PRO 5000 有设备才分别测。 | 冷加载、排队、模型推理、压缩各自 p50／p95、峰值显存和失败率；“推理 p95≤5 秒”仅为待检目标。 |
| **T2 关键帧上传** | 先测原生 App 真实手机上行及断线恢复；再用受控 Linux 发送端模拟 5 Mbit/s 等网络。只有确实边拍边传时才评估“拍完最后一批≤2 秒”；完整视频拍完才上传时记录真实完传时间。 | 原片大小、关键帧字节数、上传 p50／p95、丢包／重传、哈希一致和 0 草稿丢失。 |
| **T3 先验与坐标对齐** | 用同帧图像、内参、ARKit c2w 与深度；先做 ARKit→OpenCV 相机轴变换，再记录 WorldMirror 的首帧归一化及逆变换。 | 相似变换前后位置／旋转／尺度误差，按场景距离分桶；2 cm／1°／1% 先作为探索性目标，不能预设“直接落在 ARKit 坐标系”。 |
| **T4 缺陷检测** | 在 T5 前完成可运行版本。对独立缺陷标注和留出路径，比较 FF 空洞／多视角覆盖／位姿偏差与简易端上启发式。 | 每类缺陷召回、误报、定位误差、重建失败率；不能把模型自己填出的纹理当作覆盖真值。 |
| **T5 快环总时延** | 使用 T4 已验证的缺陷分析；首轮每段只触发一次 FF，不假装流式增量。真实 iPhone 测拍摄结束、上传、排队、推理、回传、手机首帧。 | p50／p95 及分项耗时、成功率、提示是否有用。10 秒作为快环设计目标；若超时，成长日志仍可由真实上传回执推进，预览改异步，不直接判项目失败。 |
| **T6 运动提示** | 用实际帧时间和运动；若取不到物理相机的每帧快门时长，模糊公式只算探索性代理。`ARCamera.exposureDuration` 文档描述的是虚拟内容运动模糊参数，不能未经真机核验当作物理快门真值。拉普拉斯方差受材质／焦点影响，增加人工或控制场景的清晰度真值。 | “太快”“原地转圈”“重叠不足”各自精确率、召回和好样本误触发；按设备与光照分桶。 |
| **T7 覆盖度阈值** | 必须先有 T8 的一套固定精建基线和留出路径。LiDAR 体素指标仅在支持设备上计算；普通 iPhone 用 RGB 共视／姿态代理对照。 | 覆盖指标与独立视角误差的曲线；视角数、跨度和 mm／像素阈值由曲线校准，区分 RGB 与低分辨率深度采样。 |
| **T8 SfM 初始化对比** | 同一原始采集、相同选帧、相同优化步数和计算预算比较 COLMAP、GLOMAP、ARKit 初值、FF 初值；FF 输出参与其他模型训练的许可边界先核查。 | 注册率、位姿时间、留出路径 PSNR／SSIM／LPIPS、失败场景；记录总 GPU／CPU 时间。 |
| **T9 尺度精度** | 同时跑无标记板和 ChArUco／AprilTag 校正两组；标记板真实尺寸用卷尺复核。 | 桌面、物体尺寸与尺度误差及置信区间。0.5%／1 cm 是否必要由后续机器人任务容差决定。 |
| **T10 碰撞体／MuJoCo** | 从独立几何链路导出简化网格和碰撞代理，3DGS 只作视觉层；质量、摩擦、可移动物体状态另标注。 | 除落桌稳定性，至少测桌面高度、接触/穿透、自由空间，以及一个简单 reach／place 或导航任务的可执行性；不能以 1 cm 落下通过证明 real-to-sim-to-real。 |
| **T11 手机预览／仿真** | 原生 iPhone App 的 3DGS 首帧、帧率、内存优先；浏览器 Spark／MuJoCo Wasm 只作独立研究，不替代 App 验收。若选 Spark 流式路径，采用其推荐的 RAD／`paged` 链路；若选 PlayCanvas，单独测试 Streamed SOG。 | 按真实资产大小、设备、Wi-Fi／蜂窝网络测首帧、稳定帧率、内存、发热和崩溃；网页同页仿真另列，不混入原生通过率。 |

T1／T2／T3／T6 可以在采集包形成后并行；T4 先于 T5；T8 的第一套基线先于 T7；T8／T9 先于 T10；T11 的原生查看可较早开始，仿真联动等 T10。完整 T1–T11 是研究主线，不能压成“九天已完成”的承诺。

原计划中的建议线仍保留为**事前登记的实验假设**：T1 常用帧数推理 p95≤5 秒；T2 已边拍边传时末批≤2 秒；T3 位置≤2 cm、旋转≤1°、尺度比 1±1%；T4 缺陷检出≥80%、好样本每段误报≤1；T5 同区域受限网络≤10 秒；T6 各提示命中≥80%、好样本误触发≤5%；T8 先验初始化的留出视角质量不低于纯 SfM 且位姿阶段更快；T9 校正前尺度≤2%、校正后≤0.5%、桌面高度≤1 cm；T10 1 秒内稳定、穿透≤2 mm；T11 蜂窝网络首帧≤3 秒、原生纯预览≥30 FPS，若以后单独做网页同页仿真再测≥24 FPS。这些线不得作为尚无设备或功能时的“已通过”结论，且不构成统一项目总闸门；未过线先记录场景、设备、数据量和瓶颈，评估可用的异步/降级路径。

**以下为后续原生 App 与独立传统算法阶段验收，不属于当前 T0 FF：**至少一部普通 iPhone 和一部 LiDAR 设备各提交 1 条可核验采集包；连续 10 次实际上传及至少 2 次中断恢复均不丢原件、哈希一致；至少一条同源采集分别到达 FF 预览、独立 SfM 基线和视频数据清单，并逐一标记质量。若没有 LiDAR 设备，则深度指标保持 `blocked: device_unavailable`，普通 RGB 路线照常推进。用户样本中记录第一次独立完成、第二/第三次自愿扫描与质量分布，不在 10 人小样本上做显著性结论。

## App 界面与成长记录

首屏只有“开始扫描”“我的采集”和一株小芽。扫描页显示相机画面、跟踪状态与最多一条当前提示；不以 AR 虚拟目标遮住原始画面。结束页先确认原片已保存在手机，显示室内／室外、帧数、时长、可用位姿／深度比例，之后允许上传或稍后再传。状态页严格区分 `已保存`、`上传中`、`原件已核对`、`快速预览处理中／可看／失败`、`慢环处理中／可看／失败`、`数据审核未评估／通过／拒绝`。

服务器确认一个**新的真实采集 ID 与原件哈希**后，成长日志记一次，最多三次显示播种、浇水、收获的轻交互；操作由玩家手动完成。奖励不根据自拍时长、假质量分、3DGS 就绪或训练可用性发放。游戏事件和研究标签使用独立数据表／命名空间，避免为奖励影响质量标签。衡量 10 名首次用户中有多少人无需协助完成首次上传、主动进行第二／第三次扫描，以及引导组相对普通指令组的覆盖质量；小样本只用于找明显问题，不宣称统计显著性。
