## 1. 产品决策

一次拍摄、一次上传，形成两个独立版本：

- **快速预览**：WorldMirror2 前馈重建，让用户先检查本次扫描能否形成可看的空间。
- **精细结果**：独立 SfM 求解相机，再训练／优化 3DGS，返回保留高阶颜色信息的结果。SfM 稀疏点云本身不是精细 3DGS。
- 同一采集详情只显示一个查看器，提供「快速／精细」切换和「游览」入口；算法名放在详情中。
- 精细版计算、下载或打开失败时，已有快速版仍可查看。FF 失败也不禁止独立 SfM 任务运行。
- 一次采集仅获得一次成长回执，不能因两种算法、下载、重试或升级再次奖励。
- Demo 默认由用户点击一次「优化画质」提交精细任务，控制 GPU 预算并便于观察意愿；以后可配置上传后自动启动。两条算法无需串行依赖，FF 队列优先、SfM 独立限流。本次文档更新不自动提交 GPU 任务。

精细是处理模式名称，不是保证优于 FF 的质量认证。后台必须保留失败、质量待检查和建议补拍状态。

## 3. 服务端与手机的职责

```text
iPhone：ARKit 采集、原片保存、授权上传
                 │ 稳定 HTTPS 业务 API
                 ▼
采集资产：原视频 + 帧元数据 + 源文件哈希
                 ├── FF 选帧清单 → WorldMirror2 → FF 结果版本
                 └── SfM 选帧清单 → COLMAP/SfM → GS 优化 → 精细结果版本
                                                     │
                 产物验证、格式适配、相机核对、封面、展示副本
                                                     │
                 私有文件服务／对象存储 → HTTPS 下载及缓存
                                                     │
                 iPhone Metal：SH 渲染、相机控制、游览
```

手机只连接业务入口。GPU Hub 的管理员凭据留在服务端。业务服务负责用户权限、任务持久化与结果引用，A10 负责重建，普通文件服务负责分发。先用现有业务服务承载小规模私有下载；扩大试用时改为私有对象存储、短期签名 URL，随后按流量引入 CDN。

FF 和 SfM 可以选择不同数量／分辨率的帧，但每张帧必须记录原视频 SHA-256、时间戳／帧号、变换和 JPEG 哈希。独立 SfM 比较仍不使用 FF 预测相机作为先验；若将来另做混合算法，必须单独命名并记录配置。

现有 `/v2/captures/:id/ff` 保持兼容。建议增加统一重建资源，以下是**拟议接口，不是当前可调用接口**：

- `POST /v2/captures/:id/reconstructions`：选择 `ff` 或 `sfm_gs`、固定 requestId 和处理配置。同请求幂等，显式重试生成独立 attempt。
- `GET /v2/captures/:id/reconstructions`：返回两条任务的真实状态、attempt、结果版本与可用展示档位。
- `GET /v2/reconstructions/:id/manifest`：返回归属当前用户、固定结果版本的资产清单。

结果采用不可变版本，至少含以下信息：

| 信息 | 字段内容／作用 |
|---|---|
| 来源 | captureId、sourceVideoSHA256、frameManifestSHA256、algorithm、配置／版本、Hub project/step/attempt |
| 状态 | jobStatus、artifactStatus、当前阶段、真实错误；算法成功与可展示资产就绪分开 |
| 展示文件 | variantId、format、SH degree、pointCount、byteLength、SHA-256、格式版本、鉴权下载地址 |
| 格式语义 | opacity 的 probability/logit、scale 的 linear/log、四元数顺序、SH 基与颜色处理约定 |
| 场景和相机 | bounds、initialCamera、cameraPath、内参与画幅、C2W/W2C、轴方向、模型坐标与已知／未知尺度 |
| 对齐 | modelToCanonical（可为空）、来源、拟合残差、有效性；没有测量结果时不填单位矩阵冒充已配准 |
| 审核 | qualityStatus、rendererValidationStatus；可下载不自动等于画质或机器人数据通过 |

资产路径必须绑定具体结果版本与哈希，不能用可变的 `latest.ply` 作为缓存身份。手机验证大小、格式、结构、来源及 SHA-256，临时下载完成后原子移入缓存。签名链接失效只刷新下载权限，不重新提交算法。删除采集时清理两条任务、衍生物与引用，并禁止晚到任务恢复已删除资产。

## 4. 手机画质：先保留 SfM 的真实优势

本次同视频结果提供了可用的开发基线，详见 [实测记录](VIDEO-FF-SFM-COMPARISON-2026-11-03.md)：

| 项目 | FF | SfM → gsplat MCMC |
|---|---|---|
| 输入 | 16 帧、target_size 518 | 64 帧、长边 960、7,000 步 |
| 成功任务耗时 | 54.54 秒 | 187.24 秒 |
| 高斯点数 | 490,221 | 143,064 |
| 原始 PLY | 33.34 MB、SH0 | 35.48 MB、SH3 |
| SOG | 未生成 | 3.98 MB，原生 App 暂不能解码 |

以上不是等预算评测或手机性能数据。SfM 点数更少但 PLY 更大，与它保留 SH3 等更多属性有关；压缩文件体积也不等于 GPU 内存占用。

**已核实的渲染能力：** 工程固定的 MetalSplatter revision `71ff248e…` 支持 SH0–SH3；App `readScene` 已能读取 PLY 和 splat。当前云端下载协议却只接受最多 60,000 点、32 字节/点的 SH0 splat，服务端转换会移除高阶 SH 并均匀减点。因此不能让精细版沿用此转换后宣称与服务器 SH3 画质一致。

采用以下开发顺序：

1. **FF 修正格式。** 按经过核实的来源类型解释 WorldMirror 的 probability opacity；标准 gs_mcmc PLY 继续按 logit。不能猜测所有 PLY 都相同，也不能只改一个全局 sigmoid 开关。
2. **SfM 手机保真基线。** 新增精细结果下载策略，先接入这次 143,064 点、35.48 MB 的完整 SH3 PLY，搭配最终相机。文件低于当前查看器的 100 万点／150 MiB 代码上限，但这不代表实测流畅。
3. **再决定质量档位。** 快速档可使用轻量 SH0；精细档先保留完整 SH3，再根据 iPhone 实测增加按贡献优化的点数预算、SH1/SH2 或量化版本。固定依赖的 PLY reader 检测到 `f_rest_0` 后会要求完整 45 个高阶字段；SH1/SH2 需要适配解析或选择支持的格式，不能直接删除 PLY 字段就认为可读。低档明确标识，不悄悄把所有档位降成 SH0。
4. **最后优化传输格式。** 比较 SPZ／SOG 等格式的画质、解码时间和内存。依赖库存在 SPZ 支持，但 App 白名单和验证流程尚未接通；SOG 仍需新解码适配。格式扩展必须伴随版本化解析和尺寸上限，不能仅按后缀放行。

App 继续使用原生 SwiftUI + MTKView + MetalSplatter，不引入网页作为玩家端。模型解析、解码和排序不能长时间阻塞 UI；关闭查看器应释放 GPU 资源。加载新版本时保留旧文件缓存，但不要求两份完整模型同时常驻 GPU；内存不足时释放旧 GPU 数据，失败后从缓存恢复。

## 5. 初始视角、版本切换和漫游

本次 FF 的 `extrinsics` 实际是 **OpenCV C2W**，SfM 是 **OpenCV W2C**。最终 SfM PLY 已反归一化到最终 COLMAP 世界坐标，必须匹配 `sfm-cameras-final.json`，不能使用首轮失败任务的相机。渲染器自身的居中／尺度归一化也必须一致施加到相机和模型。

初始视角优先使用本版本一个真实的重建相机及其内参／画幅，再提供物体居中视图。不要仅按包围盒猜角度，从而把正确重建展示成空白或背面。

两版本的坐标和尺度并不天然一致：

- 用共有源帧的相机对应估计 Sim(3) 对齐，检查足够的有效对应、退化轨迹、姿态一致性和残差。ARKit 公制信息只有通过同源时间关联和对齐验证后才能使用。
- 每个版本保留自身坐标，清单保存经验证的 modelToCanonical；转换查看相机时保留方向约定。若直接把旋转烘焙进 SH3 资产，还必须处理 SH 方向基，不能只旋转 xyz。
- 对齐通过时才在切换中保持同一视点；不通过时显示短暂加载并复位到新版可靠相机，保留「快速／精细」手动切换。
- 当前 FF 和 SfM 均没有已验证公制尺度。两个清单共享 captureId 并不足以证明尺度或几何一致。

首轮漫游采用 **沿本版本重建出的拍摄轨迹播放**：支持播放／暂停、拖动进度、回到起点。按源帧时间排序、连续姿态插值；跟踪断裂或异常段分段播放，不穿过缺失区域硬连成路径。未匹配模型坐标的 ARKit 原轨迹不能直接套用。

自由视角移动可以随后添加。需要避免穿墙和模拟人在地面行走时，再引入简化碰撞几何、地面、尺度与可行走区域。3DGS 外观和 SfM 稀疏点都不能直接充当机器人碰撞模型。

## 6. 大场景加载

> 2026-11-05：手机端渲染优化（测量、设备分档、排序提速、服务端手机变体与 SPZ、参考 World Labs Spark 2.0 的 LoD 流式加载）已整理为独立方案，见 [手机端 3DGS 渲染优化方案](MOBILE-3DGS-RENDERING-PLAN.md)。

本次水杯模型先全量下载并验收。大房间／街道后续采用空间分块、多级细节（LOD）和全局点数／内存预算：

1. 服务端生成粗略全景、各空间块的多级资产及含边界的索引。
2. 手机先显示粗略版，再按视锥、距离、屏幕误差和移动方向加载细节；过时请求取消或降低优先级。
3. 用磁盘缓存和 GPU 预算分别管理资产；避免长期同时渲染同区域的粗细两级导致双重透明混合。
4. 各块保留正确坐标、SH 和资产哈希；跨块深度排序／混合必须通过画面对照验收。

现有单个 SplatChunk 是渲染内存结构，不是网络 streaming。普通单文件 SOG 是压缩格式；把下载切成 HTTP Range 也不自动获得按空间加载。可参考 PlayCanvas Streamed SOG 的索引和分块规范，但原生 Metal 端仍需调度、解码及渲染适配。[官方格式](https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/streamed-sog/)

## 7. 实施批次与验收

| 批次 | 开发内容 | 完成证据 |
|---|---|---|
| A：同源双结果 | 新增 SfM 独立 job/result、来源绑定、版本化 manifest、格式适配 | 同一视频两份结果可查询下载，SHA 正确；重试不重复创建任务，删除后不复活 |
| B：手机保真 | APIClient 接受有上限的 SH3 PLY；携带匹配相机；保留 FF 缓存 | Mac Xcode 编译安装；iPhone 实际打开本次 FF 与 SfM 模型，有截图和测量记录 |
| C：两阶段体验 | 快速／精细切换、失败恢复、下载状态、轨迹播放 | 新结果失败仍能查看旧版；同一次采集仅一次成长；路径和模型一致 |
| D：性能优化 | 真机选档、压缩格式、缓存和内存释放 | 画质与资源占用有实测对照，不以文件小代替流畅 |
| E：大场景 | 空间块、LOD、预取、淘汰、跨块渲染 | 实际大场景在限定内存内连续移动，未加载区和降级状态明确 |

验收分两层：先用已有外部视频的真实结果做手机渲染基线，清楚标记为导入测试素材；随后用 iPhone App 新采集走「上传 → 两种重建 → 返回同一手机」全链路。不能把前一层写成原生拍摄验收。

手机画质对照：在相同模型版本、相机位姿、内参和输出尺寸下，保存 iPhone 渲染截图，对照服务器完整 SH3 渲染；另检查斜角／轨迹中段。区分色彩空间、曝光、裁剪、SH、透明度、排序与降点造成的差异，不把手机渲染损失误判成重建算法差异。截屏使用测试调试入口即可，不必增加产品主界面按钮。

首轮目标（待真机测量，不是现有成绩）：

- 已下载模型打开到首帧 ≤3 秒；网络下载时间单列，记录实际文件大小和网络条件。
- iPhone 17 Pro Max 连续交互／轨迹播放 60 秒，以 30 fps 为目标，记录中位数和 P95 帧时间、峰值内存、温度状态及异常。
- 真实测一次弱网中断、重新打开、缓存命中、精细失败和低内存降档；原片、回执、已完成结果都可恢复。
- FF/SfM 分别记录上传、排队、算法、打包、下载、解码、首帧时间，不把 54.54／187.24 秒当作手机端到端耗时承诺。

当前仍未完成 Xcode 编译与 iPhone 真机渲染。Windows／WSL 可验证服务、打包和数据校验；Mac＋Xcode 负责构建，真实 iPhone 负责采集和性能验收。稳定 HTTPS 上传入口、显式运行的出站 worker，以及 WorldMirror 格式适配仍是手机闭环前置工作。
